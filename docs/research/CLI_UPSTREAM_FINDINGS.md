# CLI Upstream Findings — 명령 표면의 두께, 품질 루프의 거처, canonical phase 저장

- 조사일: 2026-08-08
- Baseline: `~/.claude/plugins/marketplaces/ouroboros` @ 9486c78 (v0.50.8).
  릴리스 스냅샷이라 git 이력은 squash 1커밋 — 의도 근거는 전부 소스
  주석·문서에서 취했다.
- Evidence level: 전 항목 **Verified (source)** — file:line은 baseline 기준.
- 동기: [OPEN_QUESTIONS §8](./OPEN_QUESTIONS.md)의 두 선행 항목 — ①
  "upstream이 CLI를 얇게 둔 이유", ② canonical Stage 저장 부재의 처분
  ([progress 0004](../progress/0004_VERIFY_RECOVER_VERTICAL_SLICE.md) 질문 4).

## 1. 결론 먼저 — 질문의 전제가 부분적으로 틀렸다

OPEN_QUESTIONS §8은 "`ooo seed` CLI는 QA·승인 없이 생성·저장만 한다"고
등록했다. 실물은 다르다:

- `ooo seed`는 **전 단계 완료를 강제한다** — interview가
  `InterviewStatus.COMPLETED`가 아니면 거부하고 재개 명령을 안내한다
  (`cli/commands/seed.py:85-89`).
- **ambiguity gate를 실행한다** — 채점 후 `is_ready_for_seed` 미달이면
  대화형 선택(1 계속 인터뷰 / 2 강제 생성 / 3 취소)을 묻는다
  (`cli/commands/init.py:558,572-580`). 강제는 플래그가 아니라 **대화 중
  사용자 명시 선택**으로만 가능하고, 그 경우 `force=True`가 기록된다
  (`init.py:605`).

없는 것은 **Seed QA 루프와 채택 gate뿐**이며, 그것의 거처는 §3이 답한다.
따라서 질문은 "왜 gate가 없나"가 아니라 "왜 QA 루프가 이 명령에 없나"로
좁혀지고, 답은 우연이 아니라 계층 설계다.

## 2. 표면은 얇게, 로직은 공유 — 명문화된 원칙

CLI 명령이 얇은 것은 로직이 없어서가 아니라 **공유 핸들러에 위임해 표면 간
불일치를 막기 위해서**다. 소스에 두 번 명문화되어 있다:

- `cli/commands/qa.py:1-5` (모듈 docstring): "This command delegates to
  ``ouroboros.mcp.tools.qa.QAHandler`` **so CLI and MCP QA share the same
  judge prompt, parsing, thresholds, and result format**."
- `cli/commands/status.py:57-58`: "Layout mirrors
  ``SessionStatusHandler._handle_auto_session`` **so the CLI and MCP
  surfaces never disagree**."

`ooo seed`도 같은 패턴이다 — `init.py`의 공유 경로
`_generate_seed_from_interview`(`init.py:540`)를 재사용하는 99줄 래퍼다.
크기 분포가 이를 뒷받침한다: workflow 명령(seed 99줄, qa 109줄)은 얇고,
두꺼운 것은 설치·구동 계층(setup 5225줄, plugin 3039줄)과 **합성 계층**
(auto 1482줄)이다.

## 3. Seed QA 루프의 거처 — 두 합성 계층, 둘 다 QA를 붙인다

upstream에서 "QA 없이 Seed로 실행까지 가는" **워크플로는 없다**. QA 루프는
합성 계층 둘에 있다:

| 합성 계층 | 형태 | 근거 |
|---|---|---|
| skill `/ouroboros:seed` (대화형) | 에이전트가 MCP tool(`ouroboros_generate_seed`, `ouroboros_qa`)을 orchestrate — QA 판정·ledger·User Adoption Gate | `skills/seed/SKILL.md:5` (frontmatter `mcp_tool`), 기존 조사 [SEED_UPSTREAM_FINDINGS](./SEED_UPSTREAM_FINDINGS.md) |
| `ooo auto` (무인) | REVIEW↔REPAIR phase 루프 — 적대적 리뷰 + `GradeGate`(`required_grade` 기본 "A") + `HandlerSeedQAEvaluator` | `auto/seed_reviewer.py:1,54-55,82`, `cli/commands/auto.py:270` ("iterates Ralph until QA passes"), `auto.py:593,691`, 전이 그래프 `auto/state.py:365-373` |

`ooo seed` 단독 명령은 **재개·스크립트용 저수준 primitive**다.
`skills/seed/SKILL.md:175`가 그 용도를 직접 말한다: "Path A may run from
`ooo seed <session_id>` in a fresh conversation" — 새 대화에서 완료된
interview를 결정화하는 진입점. 그리고 `docs/architecture.md:430`:
"**In the normal flow, seeds are auto-generated by the Socratic interview**
... Most users never need to create or edit a seed manually."

무인 합성이 spec을 조용히 바꾸지 않는 것도 명문 원칙이다 —
`auto/state.py:34-52`의 SEED_REGENERATE 미배선 주석: 자동 AC 재작성은
"a reward-hacking surface (the system silently downgrades the spec the user
explicitly agreed to)"이며, 대신 예산 소진 후 BLOCKED로 사용자 선택
(re-interview / abandon)을 노출한다. "keeps the spec **owned by the
human**" — 우리 User Adoption Gate·ADR-0019와 같은 축이다.

### mcx 함의 (OPEN_QUESTIONS §8 ① 처분)

- `mcx blueprint`가 QA 루프를 항상 포함해도 **upstream use case를 부수지
  않는다** — upstream의 합성 흐름(skill·auto)도 항상 QA를 붙이고, 얇은
  primitive조차 전제 gate(전 단계 완료 + ambiguity 확인)를 갖는다.
  ADR-0019(§1 uniform QA, no skip 플래그)는 upstream 합성 동작과 정렬이다.
- 단, upstream은 ambiguity 미달에서 **사용자 대화형 강제 생성**을 허용한다
  (§1). 우리 Brief Gate `HOLD`에서의 사용자 override 표면은 Phase 6 대화형
  지점 설계(§8 잔여 항목)에서 이 전례와 대조해 결정한다 — 플래그가 아니라
  대화형 명시 선택이라는 형태가 핵심이다.

## 4. canonical phase 저장 — 합성 계층이 소유한다

"현재 어느 단계인가"의 durable 기록은 **파이프라인 합성을 소유한 층에만**
있다. 세 층이 서로 다른 것을 저장한다:

| 층 | 저장하는 것 | 근거 |
|---|---|---|
| 단계 artifact | 자기 상태만 — `InterviewStatus`(interview 상태 파일), Seed YAML(`~/.ouroboros/seeds/`), orchestrator 세션은 event sourcing + `SessionStatus`(RUNNING/PAUSED/COMPLETED/FAILED/CANCELLED — 실행 세션 수명이지 workflow 단계가 아님) | `orchestrator/session.py:1-21,234-241` |
| 개별 CLI 명령 | canonical phase를 **참조하지 않는다** — artifact 전제만 검사 (`ooo seed` → InterviewStatus, `ooo run` → seed 파일) | `seed.py:85`, `run.py` |
| 합성 (`ooo auto`) | **`AutoPipelineState.phase: AutoPhase`** — mission급 단일 JSON 문서 | `auto/state.py:441-452` |

### AutoPipelineState.phase의 실물 (`auto/state.py`)

- **닫힌 enum 12값** (`state.py:22-56`): CREATED, INTERVIEW,
  SEED_GENERATION, REVIEW, REPAIR, RUN, RALPH_HANDOFF, EVALUATE,
  UNSTUCK_LATERAL, COMPLETE, BLOCKED, FAILED. docstring: "Closed set of
  phases **for auto-mode resume and stall handling**" — 목적이 저장 이유다.
- **합법 전이 그래프** `_ALLOWED_TRANSITIONS` (`state.py:358-407`) —
  `transition()`이 매번 검증하고 위반은 예외 (`state.py:703-707`).
- **전이 시각 스탬프** — `phase_started_at`·`last_progress_at`·
  `last_progress_message`(전이 사유 문자열)를 매 전이에 기록
  (`state.py:708-713`) → stall 탐지와 phase별 timeout
  (`state.py:168-177`)의 입력.
- **저장**: `~/.ouroboros/data/auto_<id>.json`, 원자적 쓰기(temp + rename +
  fsync), owner-only 권한 (`state.py:1529-1568`). 저장 시점은 "느린 phase
  전마다" — 문서화된 이유: "resume later **without silently duplicating
  execution**" (`state.py:442-447`).
- **resume은 저장 phase로 분기하되 artifact와 교차 검증한다** —
  `pipeline.py:742-904`가 phase별로 재진입하지만, INTERVIEW phase라도
  `interview_completed`면 SEED_GENERATION으로 전진시키고
  (`pipeline.py:756-778`), Seed artifact가 없는 후반 phase는 "Cannot resume
  auto pipeline from {phase} without persisted Seed artifact"로 거부한다
  (`pipeline.py:872,1095`). **저장된 phase 단독으로는 진입을 허가하지
  않는다.**

### mcx 함의 (record 0004 질문 4 처분)

Lifecycle §3.1이 요구하는 Mission의 current Stage는 upstream 정렬로 **합성
계층(Phase 6 CLI가 첫 실물) 소유의 mission 문서**에 도입하고, enforcement
지위는 주지 않는다(진입 보증은 Gate 재계산 유지). 결정은
[ADR-0037](../adr/0037-mission-record-and-canonical-stage.md).

## 5. Phase 6 설계에 쓸 표면 전례 (결정 아님 — 대조 재료)

§8 잔여 항목("`mcx` CLI의 대화형 지점")은 대조 불가능한 신규 영역으로
등록되어 있으나, upstream CLI에 부분 전례가 있다:

- **exit code**: `ooo qa`는 판정 FAIL을 오류(1)와 구분해 **exit code 2**로
  반환한다 (`qa.py:108-109`) — HOLD exit code 설계의 직접 전례.
- **대화형 gate 선택**: ambiguity 미달 시 1/2/3 선택 프롬프트
  (`init.py:572-580`), 단계 전환마다 `Confirm.ask` (interview→seed,
  seed→run — `init.py:476,520`).
- **status 출력 계약**: 스냅샷 테스트로 고정하고("Pinned by the snapshot
  test", `status.py:54`) CLI/MCP 레이아웃을 미러링 (`status.py:57-58`).
- **표면 파리티 전략**: CLI가 MCP 핸들러를 직접 위임 호출 (§2) — 우리
  OPEN_QUESTIONS §8 "CLI와 MCP parity test 전략"의 upstream 답은
  "테스트로 맞추는 게 아니라 구현을 공유한다"이다.

## 6. 처분 요약

| 항목 | 처분 |
|---|---|
| §8 "upstream이 CLI를 얇게 둔 이유" | **닫힘** — 의도다: 표면은 공유 핸들러 위임(명문 근거 2곳), 품질 루프는 합성 계층 소유. 전제 정정: `ooo seed`도 전제 gate와 ambiguity gate는 갖는다. `mcx blueprint`의 QA 상시 포함은 upstream use case를 부수지 않는다 |
| record 0004 질문 4 "canonical Stage 저장" | **닫힘** — ADR-0037: 합성 계층 소유 mission 문서에 Phase 6 도입, enforcement는 Gate 재계산 유지 |
| §8 "`mcx` CLI의 대화형 지점" | **열림 유지** — Phase 6 설계 본문. §5의 전례를 대조 재료로 사용 |

## 7. 최상위 버전 옵션과 doctor 범위 (2026-08-23)

issue #6에서 `mcx --version`의 upstream 대응물과 진단 명령의 범위를
대조했다. 기준은 위와 같은 pinned snapshot `Q00/ouroboros` @ `9486c78`
(v0.50.8)이다.

- upstream은 `src/ouroboros/cli/main.py:141-158`에서 eager `--version`/`-V`
  callback을 등록하고, `tests/e2e/test_cli_commands.py:58-62`에서 exit 0과
  버전 출력의 존재를 검증한다.
- 버전은 upstream package `__version__`을 통해 제공된다. 우리 쪽은 이미
  hatch-vcs가 생성하는 `mission_control._version.__version__`이 패키지 버전의
  원천이므로, 별도의 버전 상수나 CLI 전용 값을 만들지 않는다.
- upstream의 `src/ouroboros/cli/commands/mcp_doctor.py:1-5,532-547`는
  `mcp` 아래의 별도 read-only 환경 진단 명령이다. Python 버전, MCP import,
  backend 의존성, Codex OAuth, EventStore, PID 상태 등 여러 check를 수행하고
  사람용/JSON 출력을 제공한다. 이것은 단순한 `--version`의 전제 점검이나
  현재 상태 요약과 같은 기능이 아니다.

### mcx 처분

`mcx --version`만 최상위 argparse metadata option으로 추가한다. 출력은
`mcx <version>`이며 mission record·journal·adapter를 건드리지 않는다. 기존
stage/verb 목록은 workflow surface로 유지하고, version flag는 별도 parser
회귀 테스트로 고정한다. `mcx status`를 doctor로 확장하거나 `mcx doctor`를
추가하는 것은 이번 issue의 범위 밖이며, 실제 preflight 요구가 생길 때
검사 항목과 실패 의미를 별도 ADR로 결정한다.
